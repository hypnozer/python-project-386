# Задача агенту: реализовать контракт приложения бронирования

Спроектируй API календаря в подходе Design First и используй `main.tsp` как
единственный источник правды. Не начинай реализацию фронтенда или бэкенда, пока
TypeSpec не компилируется и сгенерированный OpenAPI не согласован.

## Контекст

В системе один заранее заданный владелец календаря и нет регистрации или
авторизации. Владелец создает типы событий и смотрит общий список будущих
бронирований. Гость без аккаунта выбирает тип события, получает свободные слоты
на 14 календарных дат и бронирует один из них.

## Требования к контракту

1. Опиши владельца, его заранее заданное недельное расписание, тип события,
   свободный слот, данные гостя и бронирование.
2. Добавь операции для чтения владельца, создания и публичного просмотра типов
   событий, получения свободных слотов, создания бронирования и списка всех
   будущих встреч владельца.
3. Сервер должен вычислять конец встречи по длительности типа события и перед
   записью атомарно повторно проверять доступность.
4. Запрещай пересечение интервалов любых бронирований, даже для разных типов
   событий. Соседние интервалы разрешены.
5. Разделяй синтаксические ошибки, отсутствие типа события, конфликт занятого
   слота и семантически недопустимый слот стабильными HTTP-статусами и кодами.
6. Все даты окна интерпретируй в IANA-часовом поясе владельца, а точные моменты
   передавай вместе со смещением UTC.
7. Сгенерируй OpenAPI 3.1 в `openapi/openapi.yaml` и зафиксируй принятые
   допущения в `docs/domain.md`.

## Критерии приемки

- `pnpm run check` завершается без диагностик TypeSpec.
- `pnpm run compile` создает валидный `openapi/openapi.yaml`.
- Контракт покрывает все семь сценариев из таблицы в `docs/domain.md`.
- В контракте отсутствуют незаказанные сценарии регистрации, входа, отмены,
  изменения и удаления.
